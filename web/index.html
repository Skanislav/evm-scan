Add a network

Name it and the on.eth registry answers with its chain id — one eth_call on mainnet, no gateway. The registry deliberately publishes no endpoints, because an endpoint URL is where an API key lives, so that part stays yours to supply.

Most chains are not in the registry — it is new, and testnets are not its early population. Typing the id is an ordinary way in, not a failure.
Stored so a restart brings the chain back, and never returned by the API — the URL usually carries a provider's key. Before anything is written the daemon dials it and asks the node for its own chain id; if that disagrees with the number above, the network is refused. A chain reached over somebody else's RPC starts unverified: indexed and served, but never backing an on-chain commitment until you say so deliberately.
This deployment does not allow adding networks at runtime.

what a verdict costs

Approving commits a backfill down to the node's history floor, and a per-account row for every account this contract has ever touched. Marking it spam costs a row in the ledger, and is undone from here.

why there is no holder list

Discovery keeps counters and nothing else — no per-account data exists for a contract until it is promoted. That is the trade that makes watching every contract on the chain affordable, and it is why the evidence here is four numbers rather than a cluster of names.

Accounts are keyed by address; the index holds no names for them. A reverse ENS record is resolved in your browser for the rows on screen — through the Universal Resolver on your RPC, or a public one for this chain — and stands in for the address only once the forward record agrees with it.
