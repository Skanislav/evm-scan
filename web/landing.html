Permissionless asset indexing

What does this address hold?

Answered from your own node, in one call, at one block. No indexing provider in the read path.

Almost every wallet outsources this question to a handful of indexing providers — a real centralisation point in an otherwise decentralised stack, over data that is entirely public. evm-scan runs a node, indexes only what someone actually asked for, and publishes the result on-chain so nobody has to trust the indexer.

The read, end to end

This one is live, against mainnet. A hex address is checksum-checked, a name is normalised and resolved in your tab. Then pick who answers: the index, which already knows where to look and costs one request — or nothing but your own RPC, which costs twenty-one and tells no indexer who you are. Every call either way is printed on the right, with the host that saw it.

ENS

The index, readable as a name

The committed index is served as ENS text records through an ENSIP-10 wildcard resolver, so every account already has a name — nobody registers one. Ask any ENS client for evmscan.contracts and the resolver reverts OffchainLookup at the registry's own gateway; the callback hands the answer back to the registry, which checks it against the latest finalized root. A gateway can withhold an answer. It cannot forge one.

Forty hex characters is a name nobody reads, so an account can point a label at itself. That claim is an EIP-712 signature, not a transaction: a wallet holding mainnet tokens rarely holds gas on the registry's chain, and needing some is where the flow would end. The signature is carried by this deployment, which pays for it and is recorded nowhere.

A name is not an identity. The signature proves the claimant controls the address and says nothing about the label. Names are first come, first served and nothing here adjudicates them — whatever needs to know who an address belongs to has to check the address against something else.

The resolver lives on the same chain as the registry, so it proves answers against the commitment instead of signing them. A resolver on another chain could only attest — which is why this one moved.

Commitments

Which chains are committed, answered twice

The daemon will tell you what it has committed. So will the registry, to anyone with an RPC and no access to this server at all. A gateway can withhold an answer; it cannot forge one, and it cannot quietly serve a stale epoch — so the honest way to show the list is to read it both ways and print both.

AssetLens

One call, no deployment

A balance, an allowance, a symbol, decimals, an owner, a URI — one eth_call each over plain RPC. Twenty tokens is well over a hundred round trips, and because each lands at whatever block the node was on, the portfolio that comes out never existed as a state the chain was ever in. Balances summed from Transfer events are worse still: rebasing, fee-on-transfer and upgradeable tokens all make them wrong.

The lens does all of it inside one EVM execution: native balance, ERC-20 balances and allowances, ERC-165 detection, NFT ids and URIs, ERC-721Enumerable walking, and the account's own code, code hash and EIP-7702 delegation target. One round trip, one consistent snapshot — instead of a hundred calls landing at a hundred different blocks.

It is never deployed. eth_call with no to address executes creation code and returns whatever the constructor returns, so shipping the bytecode as the call payload turns a contract into a pure function. No address to trust, no upgrade key, nothing to fund on each chain.

eth_call({
  data: <AssetLens creation code> || abi.encode(request)
}, "latest")
The reply is treated as contract code

EIP-170's 24,576-byte limit applies to it, so the client batches tokens and halves the batch when a node says no. Chains differ on where that ceiling sits, which is why the limit is discovered rather than assumed.

Nonces are not in there

The EVM has no opcode for another account's nonce. It comes from eth_getTransactionCount alongside the call, and the response says whether that read landed instead of printing a confident 0.

Hostile tokens are boxed

Every inner read is a staticcall with capped gas and capped returndata. A token that stays silent comes back as unknown, never as zero — a wallet rendering a failed call as a balance of nought is a bug, not a rounding error.

Architecture

Discovery is wide and shallow; indexing is narrow and deep. The one query with no address filter only ever writes counters — the per-account index, and any history read, is reserved for promoted contracts. That asymmetry is what lets a single machine watch a whole chain.

On-chain

HintRegistry

Two dispute paths, fixed once at deployment: UMA's Optimistic Oracle V3 with a bond and a challenge window, or a local arbiter key. Either way the registry only reacts to a callback — the oracle's, or the arbiter calling resolveChallenge.

The daemon

evmscand

PostgreSQL holds candidate counters and the interactions rollup. Events enter only once deeper than the confirmation lag, so a reorg deletes a buffered row and rescans — the aggregate is never wrong.

Yours

Your own geth

Snap sync, any depth. No archive node: nothing here asks for a balance at an old block, and the indexer probes its node for the oldest block whose logs it can actually serve, then treats that as a hard floor.

eth_getLogs — receipts, for the range read eth_call — head state

require_local_node is enforced, not documented. The daemon refuses to start against a non-loopback endpoint unless you explicitly opt out.

API

Every account response carries as_of_block, so a caller can pin what it saw.

What it costs to run

Discovery is the standing cost and it only ever writes counters. Everything expensive — a per-account index, a walk back through history — is reserved for a contract something already decided was worth indexing.

Figures are the deployment's declared shape, from deploy/config.railway.yaml and the Railway runbook. CPU and memory are not benchmarked in the repo, so nothing is claimed for them here.
