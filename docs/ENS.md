# ENS: hints out, names in the client

evm-scan meets ENS twice, on two sides of the trust boundary. Hints go **out** of the
daemon: `HintResolver.sol` publishes the committed `account → contracts` index as ENS
text records, so any ENS client reads the index by name and the chain verifies what it
gets. Names come **in** only on the client: the page and the mirror turn a typed
`vitalik.eth` into an address themselves, through ENS's Universal Resolver on an RPC
the reader chose, and the daemon takes addresses only.

Both halves work on ENSv1 (mainnet) and ENSv2 (the Sepolia beta) with one code path,
because ENS deploys the Universal Resolver at the same address on every chain
(`0xeEeEEEeE14D718C2B47D9923Deab1335E144EeEe`) and both versions speak the same
interface.

## Names resolve in the client

The daemon has no endpoint that takes a name and no code that resolves one. That is a
choice, not a gap: resolution is one `eth_call` at head, which a browser or a mirror
can make against its own node as easily as the daemon could against its, and doing it
there keeps the deployment's node — a light client on the hosted profile, where every
storage slot is a verified read — out of the loop entirely. It also keeps the API's
contract simple: every `{address}` is an address.

**The page** resolves in the browser (`web/index.html`, the Names section):

1. **Universal Resolver on the reader's RPC.** `resolve(dnsEncode(name), addr(namehash))`
   on the endpoint the reader named for the lens, else a public one for the active
   chain. A Sepolia deployment resolves Sepolia (ENSv2) names; a mainnet one, mainnet.
   `ResolverNotFound` is a definite "no" and stops here.
2. **The mainnet library**, only when the resolver reported the name as offchain
   (CCIP-Read) or the RPC could not answer. It also knows GNS (`.gwei`) and WNS (`.wei`).

The result line names the path and the host, so nothing leaves the reader's chosen node
silently. Reverse records for the accounts tab go the same way — `reverse(address,
coinType)` on the Universal Resolver, which checks the forward record itself — and a
name stands in for an address only once the forward record agrees.

**The mirror** (`mirror/src/names.ts`) does the same through the `EthCall` it already
uses to read the committed root, with hand-rolled ABI pinned to blobs go-ethereum packed
from the Universal Resolver ABI (`mirror/testdata/names.json`, generated by
`internal/ens/mirror_fixtures_test.go`):

```ts
const { address, name } = await resolveName(call, "vitalik.eth");
const primary = await reverseName(call, address, chainId);   // null when none is claimed
```

Rules all three keep, the page, the mirror and the Go tools:

- **A name only ever becomes an address.** Nothing a name says enters the index or a
  mirror's rows.
- **Offchain names are reported, not followed.** A resolver that reverts `OffchainLookup`
  is answered with the gateway URLs (`OffchainNameError` in the mirror); following one is
  the client's decision, made with its own HTTP client. The page's library fallback is
  exactly that decision, disclosed.
- **Normalization is NFC + lowercase**, not ENSIP-15 (`internal/ens.Normalize`,
  `normalizeName` in both TypeScript files). Emoji sequences and confusable scripts may
  hash differently from the ENS app's rendering. The normalized form is echoed so a
  mismatch is visible.

The daemon's one ENS read is unrelated to accounts: `internal/ens` resolves
`<label>.on.eth` chain names through the chain registry so a network can be added by
name (docs/MULTICHAIN.md). It carries identity only and nothing operational.

## Hints out

```
<hex-address>.hints.<yourname>.eth
<hex-address>.<chainId>.hints.<yourname>.eth      (second label overrides the default chain)
```

`HintResolver` is an ENSIP-10 extended resolver bound at deployment to one
`HintRegistry` and one default chain id. It is set as the resolver of the label
`hints` in your name's ENSv2 subregistry. The Universal Resolver walks
root → `eth` → `<yourname>` → `hints`, finds this resolver as the deepest one on the
path, and calls `resolve(name, data)` with the full name. The account is parsed from
the first label; the `node` inside `data` is ignored, as ENSIP-10 allows.

| Record | Answer | Verified |
| --- | --- | --- |
| `addr(node)`, `addr(node, 60)` | the account itself | trivially |
| `text(node, "evmscan.contracts")` | comma-separated lowercase addresses the account touched | **on-chain**, via CCIP-Read |
| `text(node, "evmscan.epoch")` | id of the latest finalized epoch for the chain | read from the registry |
| `text(node, "evmscan.range")` | `<fromBlock>-<toBlock>` that epoch covers | read from the registry |
| `text(node, "evmscan.root")` | the epoch's index root | read from the registry |
| `text(node, "evmscan.registry")` | the HintRegistry address | immutable |
| `text(node, "evmscan.chain")` | the chain id the account was indexed on | from the name or the default |
| any other text key | `""` | — |
| any other profile | reverts `UnsupportedResolverProfile` | — |

Nothing is configured by hand: gateways, epochs and roots are read from the registry
at call time.

### How the contracts record is verified

`text(node, "evmscan.contracts")` reverts `OffchainLookup` with `sender` = the
resolver, `urls` = `HintRegistry.gateways()`, and `callData` = the same
`contractsOf(chainId, account)` calldata the registry itself issues. The daemon's
`/ccip` gateway therefore already understands the request and answers with
`abi.encode(epochId, assets, proof)`. The resolver's callback hands that answer,
unchanged, to `HintRegistry.contractsOfCallback`, which:

1. refuses anything but the **latest finalized epoch** (`StaleEpoch`),
2. recomputes the leaf from the asset list and checks the merkle proof against the
   committed root (`BadProof`, `Unsorted`),

and only then does the resolver render the list as text. A gateway can withhold an
answer but cannot forge one, and cannot serve a stale epoch. The Universal Resolver's
own CCIP reader rewrites `sender` to itself before handing the lookup to a client,
which is why the gateway does not check who is asking: the answer is verified where
it is used, not where it is fetched.

Two transient conditions are worth knowing. Before the chain has a finalized epoch,
the record reverts `NoFinalizedEpoch`. Around an epoch rollover a fetch can race the
finalization and the callback reverts `StaleEpoch`; a retry gets the new epoch.

## Sepolia runbook

Addresses of the ENSv2 beta come from
[docs.ens.domains/learn/deployments](https://docs.ens.domains/learn/deployments) and
may move; every one is a flag, and `evmscan-ens` probes each address before spending.
Only the canonical Universal Resolver `0xeEeEEEeE14D718C2B47D9923Deab1335E144EeEe`
is a default. You need a HintRegistry on Sepolia with the daemon's public gateway in
its list (docs/RAILWAY.md §1 and §3b), a funded key that owns `<yourname>.eth` on
ENSv2, and:

```bash
make build

# 1. Deploy the resolver, bound to the registry and the indexed chain.
./bin/evmscan-ens deploy-resolver -node https://<sepolia rpc> -key 0x<owner key> \
  -registry 0x<HintRegistry>

# 2. Hang it under hints.<yourname>.eth. Reuses the name's subregistry when it has
#    one; otherwise deploys a UserRegistry through the VerifiableFactory (same salt
#    ens-cli uses) and points the name at it. Idempotent.
./bin/evmscan-ens attach -node https://<sepolia rpc> -key 0x<owner key> \
  -name <yourname>.eth -resolver 0x<HintResolver> \
  -eth-registry 0x<ETHRegistry> -factory 0x<VerifiableFactory> -impl 0x<UserRegistryImpl>

# 3. Read-only check through the canonical Universal Resolver.
./bin/evmscan-ens check -node https://<sepolia rpc> \
  -name <hex-address>.hints.<yourname>.eth -registry 0x<HintRegistry>

# 4. Independent verification: ENS on one side, contractsOf on the other, must agree.
./bin/evmscan-verify -node https://<sepolia rpc> -ens <hex-address>.hints.<yourname>.eth \
  -registry 0x<HintRegistry>
```

Then set `registry.ens_parent: <yourname>.eth` in the daemon config so account responses
carry `hint_name`. That is the only thing the daemon does with the name: it formats it, it
does not resolve through it.

**The page reads the record back**, in the browser, with the same code path any ENS
client would use and none of the daemon's. The wallet tab's "as an ENS record" card
asks the Universal Resolver on the reader's RPC where the resolver sits (`findResolver`,
so the walk root → `eth` → `<yourname>` → `hints` is shown, and that it is a wildcard),
reads `evmscan.epoch`, `evmscan.range`, `evmscan.root` and `evmscan.registry` with one
`eth_call` each, then reads `evmscan.contracts`: it decodes the `OffchainLookup`, fetches
the gateway the revert named, and calls the resolver's callback, so `HintRegistry`
verifies the proof before the list is rendered. The card sets the verified list against
the live one from the API and says which contracts the last finalized commitment does
not carry yet. Every failure is explained in the resolver's terms (the table below); a
gateway that holds no copy of the finalized epoch is called out as such, because that
is what an indexer that lost its database after publishing looks like from outside.

Any ENS client works from here, with no evm-scan code:

```bash
# ens-cli
alias ens='npx "https://pkg.pr.new/ensdomains/cli/@ensdomains/cli@main"'
ens get text <hex-address>.hints.<yourname>.eth --key evmscan.contracts --chain sepolia
```

```ts
// viem
await client.getEnsText({
  name: '<hex-address>.hints.<yourname>.eth',
  key: 'evmscan.contracts',
  universalResolverAddress: '0xeEeEEEeE14D718C2B47D9923Deab1335E144EeEe',
})
```

Mixing tools: `ens … --json` prints unsigned calldata, and
`evmscan-ens send -tx '<that json>'` signs and broadcasts it with the same key.

### Reading the Universal Resolver's errors

| Error | Meaning here |
| --- | --- |
| `ResolverNotFound` | no resolver on the path, or the resolver lacks `IExtendedResolver` (the UR needs it for a wildcard match), or the `hints` label expired |
| `UnsupportedResolverProfile` | a record type the resolver does not serve (`contenthash`, …) |
| `ResolverError(NoFinalizedEpoch)` | the registry has no finalized epoch for that chain yet |
| `ResolverError(InvalidAccountLabel)` | the first label is not a 40-hex address |
| `ResolverError(StaleEpoch)` | gateway answered for an epoch that has just been superseded; retry |
| `ResolverError(BadProof)` | the gateway lied or is out of sync; the chain refused it |
| `HttpError` | the gateway did not answer (an account not in the index is a 404 there) |

## What this deliberately does not do

- No daemon-side name resolution. `GET /v1/accounts/{address}` takes an address; the page
  and the mirror resolve names before asking. This keeps the API's contract to one type
  and the deployment's node out of every reader's lookups.

- No per-asset subnames (`<symbol>.assets.<yourname>.eth`). They need a transaction
  per asset and a daemon hook; documented as future work.
- No `vitalik.eth.hints.<yourname>.eth`: resolving a nested name inside `resolve()`
  would need a nested CCIP-Read, which the Universal Resolver does not support. Resolve
  the name first, then look up the hex form; the page does exactly that.
- The daemon never follows an ERC-3668 gateway for a name. Clients do, and the
  callback verifies what they bring back.
